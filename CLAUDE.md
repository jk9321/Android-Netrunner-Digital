Android: Netrunner digital game (React + TypeScript + Vite, Cloudflare Worker hosting). Free and non-commercial; credit Null Signal Games (NSG) and NetrunnerDB. Public repo: github.com/jk9321/Android-Netrunner-Digital. Use the account name `jk9321` everywhere.

## Working style
- Act as a colleague, not a yes-man: push back when something looks wrong.
- Jeff does not work from a local clone. Never tell him to run git commands or `git pull`; say "refresh the site".
- Never write secrets or tokens into the repo.

## Branches
- Small fixes and finished work go straight to `main` (no PR per fix), then merge `main` into `beta`.
- `beta` holds ALL new AI work and all new card sets. Jeff bug-tests it on the beta Cloudflare preview. Beta merges to `main` only when Jeff says so.
- Larger work Jeff will test first goes on a named feature branch; its preview is deployed by hand (Actions -> Deploy -> Run workflow with the branch name; URL `<branch>-android-netrunner-digital.jk9321.workers.dev`).
- Never push throwaway `claude/*` branches.
- Merged branches are deleted automatically by the nightly `.github/workflows/cleanup-branches.yml` (09:17 UTC; keeps main, beta, ai-batch-results, branches with an open PR or unmerged commits). Do NOT ask Jeff to delete a merged branch. Mention a branch only if it is abandoned or parked with unmerged work and needs his decision.
- Threads with clones from before 2026-10-23 must reset to current history, never push old history.

## Rules correctness

## AI work
- Guard: `.claude/hooks/guard-ai-dir.mjs` (PreToolUse, `.claude/settings.json`) blocks Edit/Write and obvious shell writes under `src/ai/**` unless the git branch starts with `ai-`. Don't work around it; ask the coordinator for an ai-* branch thread.
- Goes through the Fable "AI Coordinator" thread for spec and review. Opus threads implement. Nothing merges to beta without its review.
- Thread economy (Jeff 2026-11-17, on trial, to save tokens). (1) One job per thread: each branch or brief gets its own build thread, which ends at its merge; the next branch starts in a fresh thread from a short hand-off file (what merged and its SHA, what is next, where the brief is), which the AI Coordinator asks the project coordinator for at the merge. (2) Batch waits: the first check is scheduled at the run's expected finish, counted from when its shards start (g1 +15 min, g3 +30, g10 +55; an ai-script run +10), and not before; after that, every 10 minutes (every 5 for a script) until it is done. Never oversleep: a check is always scheduled when a run is launched, and a finished run is read and acted on in the turn that sees it, so no result sits for hours. (3) Briefs and reports point at files instead of repeating them: a brief names the file and section, and a report is a few lines (outcome, SHA, run ids, what is needed) with the detail in a file. (4) Models: Sonnet, sparingly, for mechanical threads that need little judgment (CI checks, batch polling and logging, a recount against a written list, a small contained fix); AI logic, red teams and rules work stay on Opus, coordinators on Fable. A request for a thread says which it fits. Reviews, red teams and recounts are unchanged.
- Goal is playing strength, not matching Jeff's moves. Corp win rate should sit around 50 ± 5%.
- Counted decisions (Jeff 2026-11-10): a decision made by counting (`plan.scoreNow`, `plan.scoreInTwo`, and the ones that follow) is fixed by changing an INPUT to its count (what holds a server, the Runner's capability, the reserve), never by adding a bonus or penalty value term on top. After each counted decision ships, delete the value terms it made redundant, so the levers stay few and visible.
- One owner per quantity (Jeff 2026-11-13, after the audit found rez money priced about seven ways): every quantity the AI prices or counts (rez money, what holds a server, agenda odds, a game end, a card in hand, ...) has ONE owning function, listed in `docs/ai-priced-quantities.md` with its known duplicates. A branch may not add a second computation of a listed quantity: read the owner, or change the owner. A new rule names in its spec which listed quantities it reads; a new quantity gets a row in the same branch. The duplicate counts in that file may only go down; the review checks the file against the diff, and every audit recounts it.
- Replace, don't stack (same date): a branch that adds a counted rule names the value term or rule it replaces and deletes it in the same branch, or the hand-off says why it cannot yet and the review file records the debt. No new Corp rules and no Corp behaviour fixes until the Step 4 cleanup lands (Jeff 2026-11-14: finish the refactor first, let the win rate land where it lands, then fix behaviour; no tuning and no win-rate gate or stop line on the cleanup itself: win rate is reported only and tuning happens once, on the final product; crashes and rules errors are still fixed; his games are still pinned, as known-failing where needed); no new Runner rules until a Runner audit has filled the Runner rows of the registry.
- Tuning ladder (Jeff 2026-11-15; applies to every Corp behaviour fix, balance change and tuning step once Stage C lands, and to the Runner once it has the same shape). The levers, broadest first: (1) the counted questions, which bypass everything below them (win now, score now, the scoring line and its money, rezzes, placement) and the shared counts they read (what holds a server, the money kept for rezzing, the Runner's capability, the pools); (2) the list of ordinary moves (`/mnt/project-files/netrunner-ai/audit-fixes/stage-c/order.md`, then `src/ai/corp/candidates.ts`): its order and each line's condition; (3) the planner's settings (how many moves it compares, how far it plays forward); (4) the valuation model's numbers; (5) per-card rules in `corp/cardRules.ts`. **Trace top down, fix bottom up.** Trace: start at the top and find the layer that produced the wrong move (did a counted question take the click; did the list offer or hide the move; did the planner see it; did the valuation pick it), and write the trace in the spec. Fix: in the layer the trace found, with the narrowest change that removes the cause for the whole class of position, not only the reported game: first correct an existing thing (a wrong count input, a line's condition, a number, the order), and only then add one. A fix stays on the layer the trace found. Moving it up to a broader lever (a counted question added, or a count bent, to override a mistake made lower down) or down to a narrower one (a per-card rule or a one-position exception for a general mistake, which is whack-a-mole) needs a written reason and the approval of both the AI Coordinator and Jeff before it is built. The spec or hand-off says, for each narrower fix passed over, why it does not remove the cause. Adding a counted question, a line, a condition clause, a per-card rule, or any NEW lever (a value term, weight, threshold, switch or override that fits none of the five) needs that written reason and the AI Coordinator's approval; a new counted question and a new lever also need Jeff's yes before they are built. The review rejects a branch without them. A per-card fix has its own order (Jeff 2026-11-15): first the card's facts in its `src/ai/cards/<set>.ts` entry (what it pays, gives or gains, which the counts read), then its worth there (formula, value, counters), and only last a per-card rule or prompt answer; a fix a second card would also need is not per-card: it is a family answer or a valuation fix. Growth is counted: every stage checkpoint and audit reports the number of counted questions, lines in the list, condition clauses per line, per-card rules, planner settings and hand-set valuation numbers, and the counts go up only with a recorded reason.
- Behaviour is controlled by switches in `tuning.plan`. Folded switch names THROW when passed in `PLAN_OFF` (see `src/ai/synergy.ts`).
- Per-card AI data (synergy tags, values, profiles, effect formulas, counter worths) lives in ONE entry per card in `src/ai/cards/<set>.ts`, joined in `src/ai/cards/index.ts`. Prompt answers, break plans and run options stay in `prompts.ts` / `runs.ts`.
- Batches run on GitHub Actions: `.github/workflows/ai-batch.yml` (ref = branch name or full 40-char SHA). Use paired batches: run the base first, then pass its run id as `base_run`; compare with `scripts/corp-losses-sum.mjs`. Log every batch with `scripts/batch-log.mjs`.
- Measurement scripts on Actions (Jeff 2026-11-15): slow local runs (side-by-side on recorded states, leave-one-out, fire counts) go on `.github/workflows/ai-script.yml` instead of a container: it runs `scripts/<script>.ts` on 16 runners x 4 processes, each with `SHARD=<k>/64`, `ARGS` and `OUT_DIR`; the `out` artifact holds every shard's stdout and files. The script splits its own work by SHARD and has a summing step. It shares the 20-job limit with batches: one at a time beside a batch, and schedule the check when you launch it. Check times: a run usually finishes in 7 to 30 minutes (much faster than the same script in a container), so first check at +10 minutes, then every 5 minutes until it is done; do not use the batch check times for it.
- Batch sizes (Jeff 2026-11-07: the repo runs at most 20 Actions jobs at once, a full batch is ~600 runner-minutes): "expect identical" checks use `games=1` (any difference shows); win-rate tests start at `games=3` and top up to 10 (`game_from=3`, `add_run`) only when the result is within about 2 SE of the gate. Launch at most 2-3 batches at a time. Slot gate (Jeff 2026-11-16; `.github/scripts/batch-slot.cjs`, the `slot` job of both workflows): a batch or script run waits, holding one job, until its 16 shards fit: beside the tail of the run before when nothing is building (all 20 jobs used), with 3 jobs kept free while a CI or Deploy run is queued or running; waiting runs go short first (a 1-game check, a script), then oldest first. So a run may sit in `slot` before it starts: read the slot job's log for why, and count the check times from when the shards start. Always start the workflow from `beta` (workflow ref `beta`, the commit to test in the `ref` input), since a run started from an older branch's copy of the workflow has no gate. A waiting run is not free: it holds one of the 20 jobs until it starts, so nine waiting runs leave the running batch eleven runners for its sixteen shards. Queue discipline (2026-11-16, after the queue reached ten waiting runs): a thread keeps at most TWO runs in the queue at a time, waiting or running, and launches its next one when one of its own starts its shards; a script that will take over 30 minutes says so in its label; before launching, look at what is already waiting. Do not change the gate's ordering rule while runs are waiting: two waiting runs on different versions of the rule can each put the other first and neither starts.
- Bar before the batch (Jeff 2026-11-12): before an experiment batch is launched, the spec (or a file in `/mnt/project-files/netrunner-ai/redesign/bars/`) states the expected behaviour change and what counts as pass, fail, borderline and stop, including the behaviour numbers (not only win rate). Every arm reports its local fire count (decisions changed per game) before it gets a batch; an arm that barely fires gets a note, not a batch.
- Override check (Jeff 2026-11-12): a merge that goes ahead on a borderline or failed bar first gets a yes/no from a fresh thread that reads only the batch numbers, the bar and the diff. The AI Coordinator asks the project coordinator to start it and writes the reason for the override in the review file.
- Self-play hides holes. Pin human-usable holes with scenario tests.
- Human-games fixtures: `tests/fixtures/human-games/report-N.json` (decode bug reports with `scripts/bug-report-state.mjs`); score with `npx vite-node scripts/human-agreement.ts`.
- Branch-build failures on `ai-batch-results` are harmless noise.

## Hand-off and review
- Any branch a coordinator (AI or Multiplayer) or reviewer will check: hand off with the `handoff` skill (`.claude/skills/handoff/SKILL.md`): fixed template, evidence generated by `evidence.mjs` (diff stat vs base, files vs the spec's allowed list, diff signals, real check output), deviations listed. A prose summary is not a hand-off.
- Coordinators review with the `review` skill (`.claude/skills/review/SKILL.md`): re-run the evidence, read the raw diff against the spec, fact-check, verdict Approved/Changes needed for one full SHA. Merge only an approved SHA.
- Specs from coordinators name the allowed and forbidden files, so the evidence script can check them.
- Adversarial review (Jeff 2026-11-15; starts with the Stage C checkpoint). Two passes by a fresh thread that did not write or build the work, started by the project coordinator at the AI or Multiplayer Coordinator's request. (1) Red team on a spec or brief before it is built: "why will this fail, what does it break, what does it assume that is not true"; it reads the spec and the code, not the author's reasoning. (2) Exploit hunt at each stage checkpoint: an agent plays against the AI on purpose (or, for multiplayer, against the server) looking for repeatable exploits a person could use, and is given the list of known-failing pins so it reports new holes, not known ones. One round only: the adversary writes numbered findings to `/mnt/project-files/adversarial/<date>-<name>/findings.md`; the author or builder answers each in writing in the same file (fixed, with the commit; or disagreed, with the reason); open disputes go to the coordinator, who rules or takes them to Jeff. Jeff's checkpoint shows the findings, the fixes, and only the unresolved disputes. An exploit that is real becomes a scenario pin (known-failing if its fix waits for a later stage). The adversary changes no code, and its findings are leads until reproduced (a state, a test or a replay). Keep it light (Jeff): "nothing serious" is a valid result; each finding is marked serious (a repeatable exploit, or a flaw that would change what is built) or minor, and only serious ones need the builder's reply; the exploit hunter reads code and sets up positions and local games, and launches no batch of its own; a real exploit goes through the tuning ladder's trace and is fixed in its stage (not patched ahead of Stage D), pinned meanwhile.

## New card set process (Standard sets, newest first, on beta)
1. Pull card data and image links from NetrunnerDB.
2. Add new keywords to the hover tooltips.
3. Implement every card with its own unit test (plus liveValue/revealInHand); check errata.
   Start from `npx vite-node scripts/new-set.ts` (stubs, test todos, unknown keywords). Card scripts live in `src/core/scripts/<set>/{corp,runner}/<type>.ts`; a card with prompts declares its steps with `prompts()` (`src/core/scripts/steps.ts`) and asks only through that flow (`tests/steps.test.ts` fails on a hand-written `onPromptAnswer` or a raw step string).
3b. In a separate thread, blind rules tests with the `blind-rules-tests` skill (`.claude/skills/blind-rules-tests/SKILL.md`): 20-30 tricky cards tested from card text and the rules only, without reading the card code; real bugs go to the rules-bugs thread.
4. AI data: one entry per card in `src/ai/cards/<set>.ts`; re-tag older cards that interact. Ice that gains subroutines when encountered (Starlit Knight) needs a `gainsOnEncounter` entry, or the Runner AI prices the run against the printed subroutines only.
5. Startup/Standard legality and ban lists.
6. Make the AI use the new cards and identities: sample real NetrunnerDB decks (test-only), run `scripts/deck-playability.ts`, add one beta picker deck per new identity. Check optional "you may X now for Y later" prompts.
7. Balance with AI self-play: Corp 50 ± 5%.
